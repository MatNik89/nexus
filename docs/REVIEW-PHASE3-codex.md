# Phase 3 deep review — Codex

Target: `slice/p0-phase3` at `4bab530f4ba80f5de85f1d147379aca69b1d860e` (`a009034` + `4bab530`).

Verification run:

- `CGO_ENABLED=0 go vet ./... && CGO_ENABLED=0 go test -count=1 ./...` — PASS.
- `CGO_ENABLED=0 go test -list . ./internal/memory ./cmd/nexus` — the nine memory tests and the pre-existing conversation-only composition test were discovered.

The green suite is not sufficient for this phase gate. The implementation violates the locked persistence topology and the production memory path is either unreachable or dishonest about its effect.

1. **[HIGH] The implementation creates two profile SQLite files and persists memory outside the canonical journal.** `buildDaemon` opens the existing profile journal and then a second `memory.db` (`cmd/nexus/main.go:150-162`); the latter owns its own schema and direct transactions (`internal/memory/store.go:67-78,115-133`). HARDQ B3 and CLAUDE require **one** `~/.nexus/profiles/<p>/nexus.db` per profile, and E4/P0.3 require canonical state to originate in `EventJournal` and be reconstructed by folding events. Concrete failure: copy/replay a profile journal into a fresh profile after a crash or recovery and the accepted facts disappear, because no memory event exists in the journal; conversely, `memory.db` can contain an accepted fact for which the canonical event history has no evidence. The T18 layout test only compares two memory-store paths and therefore certifies the wrong topology. Proposed fix: put the memory tables in the one profile DB behind the daemon/journal owner and make fact state a synchronous journal projection in the same transaction.

2. **[HIGH] The newly wired production tools are unreachable: the production planner is explicitly finals-only.** `buildDaemon` registers `memory_remember` and `memory_recall` (`cmd/nexus/main.go:167-179`), but `ChatPlanner.Plan` only converts provider output into `Action{Final: ...}` (`internal/llm/planner/planner.go:102-143`) and its own header says tool-call planning is future work (`internal/llm/planner/planner.go:8-9`). Concrete failure: a real `nexus chat` request saying “remember X” can never produce a `ToolCall`, so neither memory tool executes. `TestCompositionRootServesConversation` only exercises a text response (`cmd/nexus/main_test.go:27-73`); no production-spine memory RED exists. Proposed fix: add the sealed tool-spec/provider decoding seam and an e2e `REPL -> provider tool call -> PEP -> memory -> restart -> recall` test before marking T19 complete.

3. **[HIGH] `memory_remember` cannot report an honest state-changing success, and caller-controlled metadata can disguise the write as read-only.** The tool commits through `SaveFact` and returns a `SUCCEEDED` result with no `CommitReceipt` (`internal/memory/tools.go:26-40,72-88`). The effect path correctly turns any non-read-only success without a receipt into `UNKNOWN` (`internal/kernel/effectpath/effectpath.go:443-450`). But no sealed `ToolSpec` binds this tool to `REVERSIBLE`, `ExecInProcess`, and its schema hash; dispatch trusts the provider-supplied `ToolCall` fields. Concrete failures: with the correct effect class the row commits and the turn stops as UNKNOWN; with forged `READ_ONLY`, the same write needs no idempotency key and is reported SUCCEEDED. Proposed fix: introduce the authoritative tool-spec binding at admission and return a receipt tied to the fact transaction/call/attempt.

4. **[HIGH] Tool-call profile identity is not bound to the selected store.** Both tool handlers ignore `c.ProfileID` (`internal/memory/tools.go:26-59`), while writes silently stamp `s.profile` (`internal/memory/store.go:120-123`) and `buildDaemon` captures the default profile's store (`cmd/nexus/main.go:132-178`). Concrete failure: in a work-profile daemon, a valid call declaring `ProfileID=private` is approved under the private exact-intent hash but writes to or reads from the work store. That breaks B3's immutable causal profile chain and makes the approval describe a different target than the effect. Proposed fix: reject unless call, run/session, approval, and store profile are identical; cover both recall and remember with wrong-profile REDs.

5. **[HIGH] Supersession permits diamonds and concurrent multiple successors.** `Supersede` checks only that the selected old row is accepted, outside the insertion transaction, and the schema has neither a unique constraint on `supersedes` nor a leaf check (`internal/memory/store.go:69-76,176-189`). Concrete failure: after `A -> B`, calling `Supersede(A, C, ...)` also succeeds; `Recall` then returns both B and C as “latest”. Two sessions racing to correct A can produce the same state because both prechecks complete before either insert. Proposed fix: enforce one successor per fact with a DB constraint and perform accepted-leaf validation plus insertion in one `BEGIN IMMEDIATE` transaction; reject superseding an already-superseded node.

6. **[MED] The public `Search` retrieval path leaks superseded content.** `Recall` excludes accepted rows with an accepted successor (`internal/memory/store.go:199-205`), but `Search` filters only `status='accepted'` (`internal/memory/store.go:221-225`). Concrete failure: after correcting “server is 10.0.0.1” to “server is 10.0.0.2”, `Search("server")` returns both values, allowing stale facts back into any future caller that uses this public retrieval API. Proposed fix: share one authoritative latest-accepted query/view between every model-facing retrieval path and add a stale-search RED.

7. **[MED] Stored provenance, trust, and sensitivity are discarded and later promoted to a blanket trusted/internal observation.** A fact row retains only ID/profile/content/origin/status (`internal/memory/store.go:40-47`); recall emits every result as `TOOL_TRUSTED` and `INTERNAL`, with lineage only to the recall call (`internal/memory/tools.go:72-79`). Concrete failure: an inferred fact derived from `UNTRUSTED_EXTERNAL` content can be accepted and recalled as `TOOL_TRUSTED`, bypassing the assembler's untrusted fence; a fact containing a known secret is relabeled INTERNAL and copied verbatim into the next provider prompt. This violates the monotone trust/lineage rule. Proposed fix: persist source lineage, trust, and sensitivity, combine them monotonically on recall, and apply the known-ref policy before any provider/journal boundary.

8. **[MED] The locked exact/tag retrieval surface is absent.** The schema has no tag representation and exposes only FTS phrase matching ordered by rowid (`internal/memory/store.go:69-78,194-230`), although T19/HARDQ B8 require deterministic recency plus exact/tag retrieval. Concrete failure: the user stores two facts with the same phrase but different intended tags; there is no API capable of selecting the requested tag, and an “exact” lookup is tokenizer-dependent rather than byte-exact. Proposed fix: add the smallest typed tag/exact lookup fields and deterministic queries, with REDs for tag isolation and byte-exact selection. Do not add embeddings or decay.

9. **[MED] `Store.Open` does not own or verify the B3 path boundary and follows the final database-file symlink.** It accepts an arbitrary path and creates the memory schema before establishing the profile binding (`internal/memory/store.go:56-99`). The only containment proof is in a test helper (`internal/memory/store_test.go:19-33`), and its layout assertion is substring-based (`internal/memory/store_test.go:81-94`). Concrete failure: a future caller can open `system/nexus.db` or a symlink to another fresh file as profile `work`; `Open` creates profile payload there and stamps it as valid, violating “system DB has zero profile payloads”. Proposed fix: derive the sole profile DB path from a trusted `pathx.Layout` at the owner boundary and open the final component no-follow/pinned; enumerate the system DB in the negative RED rather than checking a returned string.

10. **[MED] One long memory operation can block every daemon session and cannot be cancelled.** The shared store has one connection (`internal/memory/store.go:62-66`), all DB methods are context-free, both handlers ignore their `ctx`, and recall/search have no result or work bound (`internal/memory/store.go:194-230`; `internal/memory/tools.go:26-59`). Concrete failure: a disconnected client issues a pathological/large FTS recall; the query continues while every other UDS session queues indefinitely for the sole connection. This is head-of-line blocking, not a `SQLITE_BUSY`, so the existing concurrency gate misses it. Proposed fix: use `QueryContext`/`BeginTx`, propagate the S7 context, and impose input/result/work budgets.

11. **[MED] The T18 “restart+replay” RED does not exercise replay, and the approval RED bypasses the production approval owner.** `TestProfileStampImmutableAcrossRestart` merely closes and reopens the standalone memory DB (`internal/memory/store_test.go:96-121`); no journal replay occurs. `TestRememberPreviewAndApprovalGate` calls `Propose` and `Accept` directly (`internal/memory/facts_test.go:17-35`), while production `memory_remember` bypasses both and calls `SaveFact` after PEP (`internal/memory/tools.go:33-39`). Concrete failure: deleting/corrupting `memory.db` while retaining a valid journal still leaves every named RED green, and a regression in exact-intent approval-to-content binding is invisible. Proposed fix: make the ledger REDs cross the real journal/projection and PEP seams, including a one-byte content mutation under an old approval.

12. **[LOW] The daemon never closes the memory store.** `buildDaemon` opens `memStore`, but both the `daemon.New` error path and the returned shutdown handle close only the journal (`cmd/nexus/main.go:162-186`); the composition test does the same (`cmd/nexus/main_test.go:51-55`). Concrete failure: repeated daemon construction in one process leaks SQLite handles/WAL resources, and orderly shutdown does not run the memory owner's close/checkpoint path. Proposed fix: return/own one aggregate closer and close the memory store on every failure and shutdown path.

No FTS injection was found in the reviewed query construction: SQL uses a bound `MATCH` parameter and embedded phrase quotes are doubled (`internal/memory/store.go:198-205,220-225`). That does not mitigate the unbounded-query finding above.

VERDICT: FAIL
