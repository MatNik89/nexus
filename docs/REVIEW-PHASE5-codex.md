# Phase 5 deep review and security integration review

Revision reviewed: `f63143ca864b400a9118ce7f82d1507700cdf8c8` on `slice/p0-phase5`, covering commits `9606515`, `63f2314`, and `f63143c` in the requested scope.

Result: **FAIL**. The committed suite and vet are green, but clean-HEAD negative probes reproduced multiple attacker-reachable contract violations. Most importantly, T24 is not integrated with the loop at all, and T22 can either discard an admitted update or blindly repeat a remotely accepted send.

## Findings

1. **[HIGH] T24 does not suspend or resume a real turn.** `RunChannelTurn` constructs a fresh in-memory effect-path approval set and gives the loop no durable approval store (`internal/app/daemon/daemon.go:207-223`). On `ErrNeedsApproval`, the loop calls `failTurn`, appends a failed turn, and exits (`internal/kernel/loop/loop.go:279-285`); it never calls `approval.Store.Suspend`. Production references confirm that `Suspend` and `SuspendedTurn` are called only by tests (`internal/approval/approval.go:250-275`, `internal/approval/approval.go:359-375`). The Telegram approval command merely changes a manually pre-created row and promises a resume that has no caller (`cmd/nexus/main.go:463-468`). **Concrete failure:** an irreversible Telegram request reaches `DecisionAsk`, is recorded as `TurnFailed`, receives no usable challenge, and cannot resume after approval or daemon restart. The manually orchestrated test creates and consumes the challenge itself instead of exercising the loop (`cmd/nexus/main_test.go:385-410`). T24 acceptance is not met.

2. **[HIGH] The durable inbox has no terminal outcome, so a crash can permanently discard a request.** The inbox schema stores only the admitted text and status (`internal/channel/channel.go:157-166`); the only inbound projection transition inserts `ADMITTED`, with no `TERMINAL` event or stored handler outcome (`internal/channel/channel.go:191-204`). On every duplicate, `Admit` returns only `Replayed=true` (`internal/channel/channel.go:310-329`), and Telegram then skips the handler unconditionally (`internal/channel/telegram/telegram.go:182-191`). `EnqueueReply` is an unrelated append with no inbound message identifier and no terminal transition (`internal/channel/channel.go:332-352`). **Concrete failure:** crash after admission but before handler execution; Telegram redelivers the update, replay suppresses the handler, and the message is lost forever. A clean-HEAD probe that admitted first and then redelivered through `PollOnce` failed with `handler runs=0`. The same gap loses a reply after a crash between handler completion and enqueue. `TestOutboxRecipeAtomicUnderSigkill` counts `EvOutboundEnqueued` as the alleged terminal half (`internal/channel/channel_test.go:133-159`), so it does not test the ledger's terminal-result-plus-outbox recipe.

3. **[HIGH] An accepted Telegram send can be blindly repeated when the HTTP result is ambiguous.** `Core.Flush` treats every callback error as proof that nothing was accepted and leaves the row `PENDING` (`internal/channel/channel.go:392-407`). Telegram returns an error for a lost/malformed response after issuing the HTTP request (`internal/channel/telegram/telegram.go:102-132`), even though Telegram may already have accepted `sendMessage`. **Concrete failure:** Telegram commits the message, the response connection resets, `Flush` leaves the row pending, and the next tick sends the same message again. A clean-HEAD probe failed with `accepted delivery retried blindly: accepts=2`. This violates B2 delivery honesty.

4. **[HIGH] Failure of both the sent mark and UNKNOWN mark leaves a remotely accepted delivery durably retryable.** After transport success, `Flush` tries `SENT` and then `UNKNOWN`, but if both journal writes fail it only returns an error (`internal/channel/channel.go:408-422`). The comment claims an in-memory park, but no such state exists; the durable row remains `PENDING`. **Concrete failure:** Telegram accepts the send and the journal becomes unavailable; after restart the pending row is sent again. A clean-HEAD close/reopen probe failed with `accepted delivery retried after both marks failed: accepts=2`.

5. **[HIGH] Approval authority is not bound to the originating principal or channel, and bound Telegram groups turn every member into the owner.** A suspended challenge stores no expected source, chat, or principal (`internal/approval/approval.go:71-83`, `internal/approval/approval.go:136-148`). `Approve` accepts any non-empty source and the projection checks only challenge status (`internal/approval/approval.go:313-338`, `internal/approval/approval.go:173-185`). `pending` returns every challenge in the profile to any bound chat (`cmd/nexus/main.go:475-487`). The Telegram update model records only `chat.id`, not `from.id` or chat type (`internal/channel/telegram/telegram.go:88-99`), and all text from that chat becomes `TrustUser` (`internal/app/daemon/daemon.go:236-244`). **Concrete failure:** any participant in a configured group chat lists a private destructive target and replies `approve ch-...`; the store accepts `tg:chat-<group>` even if the challenge originated elsewhere. A clean-HEAD probe using a foreign chat source failed because the foreign source successfully approved. Separate per-profile database files prevent the tested work/private database crossing, but they do not satisfy the required same-principal-and-channel binding.

6. **[HIGH] The approval hash cannot provide the required destructive-filesystem exact-intent binding.** `effectHash` binds tool ID, raw argument bytes, schema hash, effect class, execution kind, idempotency key, and profile (`internal/approval/approval.go:51-67`). Neither `ToolCall` nor the challenge stores the resolved target resource, `(device,inode)`, originating principal/channel, or proof that policy returned `DecisionAsk`. **Concrete failure:** the owner approves deletion of `/safe/link`; before execution an attacker swaps that path to another inode, while the approved raw arguments and hash remain unchanged. The approval layer also cannot distinguish an ASK-classified effect from a DENY-classified one if a caller creates a challenge directly. The modified-arguments test is causal—it failed when argument bytes were removed from the hash—but it proves only a subset of C4.

7. **[MED] Approval expiry is not enforced at consumption and is racy at decision time.** The approval transition checks expiry before the journal transaction and uses `now > expires` (`internal/approval/approval.go:313-332`), while `Pending` excludes `expires == now` (`internal/approval/approval.go:277-294`). `ConsumeApproval` performs no expiry check at all (`internal/approval/approval.go:346-356`). **Concrete failure:** approve just before expiration, wait indefinitely, then consume successfully; or approve exactly at the boundary that `Pending` already considers expired. Clean-HEAD probes reproduced both: `expired approval remained consumable` and `approval accepted at the excluded expiry boundary`.

8. **[MED] Approval summaries bypass the journal redactor and can expose tool secrets to Telegram.** `Suspend` interpolates raw argument JSON into `summary`, appends it, and returns the original unredacted string (`internal/approval/approval.go:260-274`). Telegram's `pending` command emits that returned/projected summary (`cmd/nexus/main.go:475-486`). The committed summary test uses a no-op redactor and checks only that path text is present (`internal/approval/approval_test.go:210-223`). **Concrete failure:** arguments containing a configured API key are redacted in the journal event but remain in the returned challenge shown to the user. A clean-HEAD known-secret probe failed with `returned approval summary exposes a known secret`.

9. **[MED] Telegram transport errors disclose the bot token.** The token is embedded in the request URL (`internal/channel/telegram/telegram.go:102-108`) and the wrapped `http.Client.Do` error is returned verbatim (`internal/channel/telegram/telegram.go:113-115`). `Probe` copies that error into its detail (`internal/channel/telegram/telegram.go:245-254`). **Concrete failure:** a DNS/TLS/dial error renders `https://api.telegram.org/bot<token>/getMe` in an error or future closure report. A clean-HEAD failing-transport probe observed the complete test token in the returned error.

10. **[MED] The claimed live channel probe is never registered into the T11 closure snapshot.** `Adapter.Probe` exists (`internal/channel/telegram/telegram.go:243-262`), but production startup only constructs and runs the adapter (`cmd/nexus/main.go:163-180`); there is no production call or registration. The only executable coverage invokes the method directly (`internal/channel/telegram/telegram_test.go:246-257`). **Concrete failure:** invalid/revoked bot credentials do not make the startup closure snapshot fail, so readiness can claim a state that has never probed the external channel.

11. **[MED] Several ledger RED claims are absent or non-causal, allowing the above defects to remain green.** T22 has two single-transaction kill tests, not the required crash matrix across admission, effect, offset, and remote acceptance; its outbox recipe has no terminal result (`internal/channel/channel_test.go:87-174`). `TestExactlyOnceAdmission` is sequential (`internal/channel/channel_test.go:53-84`) and stayed green after deleting the database `UNIQUE(adapter_id, channel_identity, update_id)` race backstop. T24's restart test restarts only an approval store and manually consumes a call (`internal/approval/approval_test.go:61-99`), not a daemon turn. The F2 portion sends plain text to an echo-only provider (`cmd/nexus/main_test.go:412-429`) and stayed green after ablating `RunChannelTurn` from `ModeDefault` to `ModeYolo`. **Concrete failure:** a regression that enables channel yolo or removes concurrent admission serialization is not detected by the tests advertised for those properties.

12. **[LOW] The challenge identifier has only a deterministic 64-bit hash prefix.** The ID is `ch-` plus 16 hexadecimal characters of the effect hash (`internal/approval/approval.go:260-267`). The full 256-bit effect hash is rechecked on consumption (`internal/approval/approval.go:199-213`), so a prefix collision does not authorize a different effect; it causes challenge primary-key collision/denial of service. **Concrete failure:** after roughly birthday-bound chosen-intent work, a colliding challenge cannot be inserted. This is not the principal authorization break, but it is weaker than a random single-use challenge nonce and couples public lookup identity to intent.

13. **[LOW] Binding parsing silently accepts ambiguous local configuration.** `NEXUS_TELEGRAM_BINDINGS` silently skips malformed entries and uses last-write-wins for duplicate chat IDs without trimming either side of `=` (`cmd/nexus/main.go:431-450`). Adapter construction later rejects invalid profile slugs (`internal/channel/telegram/telegram.go:71-78`), so malformed input fails closed rather than crossing profiles, and the environment is not remotely attacker-controlled. **Concrete failure:** `42=private,42=work` silently remaps chat 42 according to ordering; whitespace such as `42= private` disables the adapter rather than identifying the bad entry. This is an operational ambiguity, not a demonstrated external privilege escalation.

14. **[LOW] Channel messages carry false REPL provenance.** `RunChannelTurn` passes Telegram text through `userBlock`, which hard-codes `SourceURI: nexus://repl` and `Producer: repl` (`internal/app/daemon/daemon.go:227-244`). **Concrete failure:** journal/context inspection cannot distinguish terminal input from Telegram input, weakening incident attribution and future source-sensitive policy. `TrustUser` is appropriate only for an authenticated, single-owner bound chat; finding 5 shows that the current adapter also permits group members to inherit that trust.

## Security target disposition

- Exactly-once admission: the unique projection constraint plus append fallback prevent a demonstrated concurrent double-handler path, but the committed RED does not exercise the race. Crash/redelivery instead produces an at-most-once/lost-work failure (finding 2).
- Delivery honesty: failed; ambiguous transport results and dual mark failure both create blind retries (findings 3-4).
- Profile chain: separate profile journals and adapter-profile comparison prevent the tested cross-profile lookup. Same-profile principal/channel authorization and group sender identity fail (finding 5). Binding environment parsing is local and fail-closed for invalid profiles, with the low operational ambiguity in finding 13.
- HITL: consume-without-approve and sequential replay fail closed through the `status='APPROVED'`/`status='PENDING'` guards. Source binding, expiry, exact target identity, real suspension, and resume fail. The 64-bit challenge prefix is a collision-DoS concern rather than an approval-preimage bypass because consumption checks the full hash.
- F2: production `RunChannelTurn` currently selects `ModeDefault`, and no text parser toggles yolo. No present approval-to-execution integration exists, so Telegram cannot currently execute either ASK or DENY through T24. The committed F2 test is non-causal and the approval record lacks a policy-decision binding, so the promised invariant is not regression-protected.
- Injection: private owner-chat text may legitimately be `USER` trust. Because group chats/senders are not distinguished, attacker-controlled group-member text can also reach the planner as `USER` (finding 5). Non-text messages are correctly refused and that branch test is causal.
- Offset handling: the in-memory offset advances only after `processUpdate` returns, but restart/partial-batch replay is unsafe because admitted messages have no terminal outcome (finding 2), while unbound/non-text refusals are never admitted and can enqueue duplicate refusals on redelivery (`internal/channel/telegram/telegram.go:137-181`).
