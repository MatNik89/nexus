Therefore an ordinary crash cannot durably commit an event without its projection row and checkpoint, or advance the checkpoint without both. `Open` verifies the journal under the writer lease and catches each projection up before starting the actor (`internal/kernel/journal/journal.go:288-319`); catch-up applies one event and advances its checkpoint in the same replay transaction (`internal/kernel/journal/journal.go:322-367`). The production RED drops both memory tables and the checkpoint, then reconstructs ordinary rows and FTS; the second RED additionally reconstructs rejected state and the accepted supersession leaf (`internal/memory/store_test.go:120-178,242-257`; `internal/memory/facts_test.go:311-349`). Reverting catch-up makes these REDs fail.

2. **[NEW-ERROR] The new checkpoint/lineage schema has no upgrade path for a database produced by the immediately preceding revision.** At `c05bb8b`, `mem_facts` can already contain rows but has neither `lineage` nor `proj_sync_offsets`. This is not the atomic-crash window—the new append transaction is sound—but it makes the fold unable to open its direct predecessor's durable state. Add a projection schema/version owner that atomically drops/rebuilds derived tables from the canonical stream (or performs a compatible migration) before seeding checkpoint zero; add a `c05bb8b` fixture upgrade RED.
